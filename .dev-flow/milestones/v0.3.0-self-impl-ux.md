# v0.3.0: Phase 2 — 自实现 UX 层（v1）

## Context
Phase 1（整合版）已完成：实现了完整的「版本管理 → 依赖 → 运行 → 诊断」主线，底层全走 shell 调用（Coursier CLI、jstat/jcmd）。
Phase 2 是「自实现 UX 层」的第一个里程碑，核心目标：拆分 workspace 多 crate 架构 + 内嵌依赖解析替换 shell 调用 + 诊断输出结构化。
版本类型：minor（新功能 + 架构重构，向后兼容）

Start Commit: 83d324b41155b78271dde7e0172d159fedbb34c7

## 产品边界
**本阶段做什么：**
- Workspace 多 crate 拆分（jex-core + jex-cli）
- 内嵌依赖解析：用 coursier-core Rust API 替代 shell `cs` 调用，用户无需预装 Coursier CLI
- 诊断结构化：解析 jstat/jcmd 输出为结构化数据，改进线程计数准确性
- 诊断 TUI：用 ratatui 为 gc/threads 提供实时交互界面
**不做什么：**
- 不实现火焰图（Phase 2.3）
- 不实现 JFR 自解析（Phase 2.4）
- 不实现诊断增强面板（Phase 2.5）

## 子任务详细设计

### 1 Workspace 多 crate 拆分（jex-core + jex-cli）

- **功能目标**：将单 crate 拆分为 workspace，分离核心逻辑与 CLI 入口，为后续内嵌依赖（coursier-core）提供独立 crate 载体
- **文件结构**：
  - 新建 `crates/jex-core/` — 核心逻辑库（deps/jdk/run/diag/export/search/util/error/config）
  - 新建 `crates/jex-cli/` — CLI 入口 + clap 路由（main.rs + Commands 枚举）
  - 修改根 `Cargo.toml` 为 workspace manifest
  - `crates/jex-core/Cargo.toml` — 库名 jex-core，依赖 toml/serde/serde_json
  - `crates/jex-cli/Cargo.toml` — 二进制 jex，依赖 jex-core + clap
- **接口设计**：
  - `jex-core` 导出所有公共模块（pub mod jdk, deps, run, diag, export, search, util, error, config）
  - `jex-cli` 仅包含 main.rs 和 CLI 类型定义，通过 `use jex_core::*` 引用核心功能
- **后端流程**：
  1. 创建 workspace 结构
  2. 将 src/ 下所有模块移动到 crates/jex-core/src/
  3. 从 main.rs 提取 Commands 枚举到 crates/jex-cli/src/main.rs
  4. 配置 Cargo workspace（成员、依赖路径）
  5. 确保 `cargo check`、`cargo test`、`cargo clippy` 全部通过
- **测试标准**：`cargo check` + `cargo test` + `cargo clippy -- -D warnings` 全部通过
- **提交信息**：`refactor(workspace): split into jex-core + jex-cli crates`

### 2 自动下载 cs CLI + 保持 shell 调用

- **功能目标**：jex 首次使用时自动下载 Coursier CLI（`cs`）到 `~/.jex/bin/`，用户无需手动安装，保留 Coursier 完整依赖解析能力
- **文件结构**：
  - 修改 `crates/jex-core/src/config.rs` — 新增 `ensure_cs()` 函数（检查 + 下载）
  - 修改 `crates/jex-core/src/deps.rs` — `resolve_latest_version` 调用前先 `ensure_cs()?`
  - 修改 `crates/jex-core/src/run.rs` — `build_classpath` 调用前先 `ensure_cs()?`
- **接口设计**：
  - `config::ensure_cs() -> Result<PathBuf>` — 返回 `cs` 可执行文件路径
  - 内部逻辑：检查 `~/.jex/bin/cs` 是否存在 → 不存在则从 GitHub Releases 下载 → 返回路径
- **后端流程**：
  1. 检查 `~/.jex/bin/cs` 是否存在且可执行
  2. 不存在：根据 `std::env::consts::OS` 和 `ARCH` 构造下载 URL
     - `https://github.com/coursier/coursier/releases/latest/download/cs-{os}-{arch}`
     - Linux: `cs-linux-amd64`，macOS: `cs-macos-arm64` / `cs-macos-amd64`
  3. 用 `curl` 或 `reqwest` 下载到 `~/.jex/bin/cs`
  4. 设置可执行权限（`chmod +x`）
  5. 返回 `~/.jex/bin/cs` 路径
  6. 后续 `deps.rs` / `run.rs` 中的 `Command::new("cs")` 改为 `Command::new(&cs_path)`
- **测试标准**：`cargo check` + `cargo test` + `cargo clippy -- -D warnings` 全部通过
- **提交信息**：`feat(deps): auto-download cs CLI on first use`

### 3 诊断结构化（jstat/jcmd 输出解析 + 线程计数修正）

- **功能目标**：将 jstat/jcmd 的文本输出解析为结构化数据（Rust struct），改进线程计数准确性，为后续诊断增强（火焰图、JFR）打基础
- **文件结构**：
  - 修改 `crates/jex-core/src/diag.rs` — 重构为结构化解析
- **接口设计**：
  - `diag::gc(pid) -> Result<()>` 签名不变（CLI 输出保持不变）
  - `diag::threads(pid) -> Result<()>` 签名不变
  - 新增内部结构体（不暴露公共 API）：
    - `GcSnapshot { timestamp, s0, s1, eden, old, meta, ... }` — jstat -gcutil 解析结果
    - `ThreadInfo { name, state, daemon, blocked }` — 单线程信息
    - `ThreadSnapshot { threads: Vec<ThreadInfo>, total, daemon_count, blocked_count }`
- **后端流程**：
  1. `gc()` 解析 jstat -gcutil 文本输出为 `Vec<GcSnapshot>`，格式化为表格输出
  2. `threads()` 解析 jcmd Thread.print 文本输出为 `ThreadSnapshot`：
     - 使用正则或状态机匹配线程声明行 `"name" #N daemon prio=...`
     - 准确统计线程状态（RUNNABLE/BLOCKED/WAITING/TIMED_WAITING）
     - 死锁检测：匹配 `Found one Java-level deadlock` 段落
  3. 格式化输出保持现有风格（人类可读）
- **测试标准**：`cargo check` + `cargo test` + `cargo clippy -- -D warnings` 全部通过
- **提交信息**：`feat(diag): structured parsing for jstat/jcmd output`

### 4 诊断 TUI（ratatui：gc 实时监控 + threads 线程列表）

- **功能目标**：用 ratatui 为 `jex java gc` 和 `jex java threads` 提供实时交互式 TUI 界面，替代纯文本 `println!` 输出
- **文件结构**：
  - 修改 `crates/jex-core/Cargo.toml` 添加 ratatui + crossterm 依赖
  - 修改 `crates/jex-core/src/diag.rs` — 新增 TUI 渲染函数
  - 修改 `crates/jex-cli/src/main.rs` — gc/threads 子命令调用 TUI 渲染
- **接口设计**：
  - `diag::gc_tui(pid) -> Result<()>` — 启动 ratatui App，实时刷新 GC 数据
  - `diag::threads_tui(pid) -> Result<()>` — 启动 ratatui App，显示线程列表
  - 保留 `diag::gc(pid)` 和 `diag::threads(pid)` 作为纯文本 fallback（`--no-tui` 或非终端环境）
- **交互设计**：
  - **GC 监控 TUI**：
    - 顶部标题栏：`JVM GC 监控 (PID: {pid})`
    - 中间表格：列 = S0% | S1% | Eden% | Old% | Meta% | YGC | YGCT | FGC | FGCT
    - 底部状态栏：按 `q` 退出，按 `p` 暂停/继续刷新
    - 刷新频率：1 秒（与 jstat -gcutil 1000 一致）
  - **线程列表 TUI**：
    - 顶部标题栏：`JVM 线程信息 (PID: {pid})`
    - 中间可滚动列表：列 = 线程名 | 状态 | 守护线程
    - 状态着色：🟢 RUNNABLE | 🔴 BLOCKED | 🟡 WAITING/TIMED_WAITING | ⚪ TERMINATED
    - 底部统计栏：总线程数 / 守护线程 / BLOCKED 数
    - 按 `q` 退出，方向键/滚轮滚动
- **后端流程**：
  1. 复用子任务3 的结构化解析（GcSnapshot / ThreadSnapshot）
  2. ratatui 渲染循环：Event → Update State → Draw
  3. crossterm 处理终端事件（按键、窗口大小变化）
  4. 退出时恢复终端原始状态
- **测试标准**：`cargo check` + `cargo test` + `cargo clippy -- -D warnings` 全部通过
- **提交信息**：`feat(diag): add ratatui TUI for gc and threads monitoring`
