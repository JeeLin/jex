# v0.12.0: 生态互通（import pom）

## Context
Phase 0–2 全部完成（v0.2.0–v0.7.0），Phase 3 已完成脚本模式（v0.9.0）、自更新（v0.10.0）、CLI 增强（v0.11.0）。生态互通的 export maven（jex.lock.toml → pom.xml）在 v0.2.0 已实现，本里程碑补全反向能力：从 pom.xml 导入依赖到 jex.toml，完成 export/import 闭环，降低 Maven 项目迁移到 jex 的成本。

版本类型：minor（新功能）

## 产品边界

### 做什么
- `jex import maven` 命令：解析 pom.xml，提取依赖，写入 jex.toml
- 支持 pom.xml 中的 `<dependencies>` 和 `<dependencyManagement>` 解析
- 处理已有 jex.toml 的合并策略（已有依赖不覆盖，新依赖追加）
- 生成/更新 jex.lock.toml（锁定导入的依赖版本）

### 不做什么
- 不解析 pom.xml 的完整 Maven 模型（plugin、profile、parent 等）
- 不做反向同步（import 是一次性的，不建立 pom.xml ↔ jex.toml 持续同步）
- 不处理 Gradle build 文件（后续里程碑）
- 不做 Maven 仓库认证（使用默认公共仓库）

## 子任务详细设计

### 1 pom.xml 解析引擎

- **功能目标**：解析 pom.xml 文件，提取 `<dependencies>` 和 `<dependencyManagement>` 中的依赖声明
- **文件结构**
  - 新建 `crates/jex-core/src/import.rs`：导入模块核心逻辑
  - 修改 `crates/jex-core/src/lib.rs`：导出 import 模块
- **接口设计**
  - 函数：`pub fn parse_pom(path: &Path) -> Result<Vec<PomDependency>>`
  - 结构体：
    ```rust
    pub struct PomDependency {
        pub group_id: String,
        pub artifact_id: String,
        pub version: Option<String>,  // 可能由 dependencyManagement 管理
        pub scope: Option<String>,    // compile/test/provided 等
    }
    ```
  - 使用已有的 `quick-xml` 依赖解析 XML（项目已引入）
- **后端流程**
  1. 读取 pom.xml 文件内容
  2. 用 quick-xml 逐元素解析 `<project>` → `<dependencies>` → `<dependency>`
  3. 提取 `<groupId>`、`<artifactId>`、`<version>`、`<scope>`
  4. 同时解析 `<dependencyManagement>` 中的版本管理声明
  5. 将 dependencyManagement 的版本号应用到未指定版本的依赖
  6. 过滤 scope=provided/test/runtime 的依赖（只导入 compile scope）
- **测试标准**
  - 单元测试：解析含 dependencyManagement 的 pom.xml
  - 单元测试：解析含 scope 过滤的 pom.xml
  - 单元测试：空依赖 pom.xml
  - 边界测试：缺少 version 的依赖（由 dependencyManagement 管理）
- **提交信息**：`feat: add pom.xml parser for dependency import`

### 2 依赖提取与坐标转换

- **功能目标**：将解析出的 PomDependency 转换为 jex 格式的坐标（group:artifact:version），并提取传递依赖
- **文件结构**
  - 修改 `crates/jex-core/src/import.rs`：添加坐标转换和传递依赖解析
- **接口设计**
  - 函数：`pub fn pom_to_jex_coords(deps: &[PomDependency]) -> Vec<String>`
  - 函数：`pub fn resolve_transitive(deps: &[PomDependency]) -> Result<Vec<PomDependency>>`
- **后端流程**
  1. 将 `group_id:artifact_id:version` 格式化为 jex 坐标字符串
  2. 对未指定版本的依赖，通过 Maven Central search API 查询最新版本
  3. 使用已有的 resolver 模块解析传递依赖
  4. 去重（同一 artifact 只保留一个版本，优先用显式声明的版本）
- **测试标准**
  - 单元测试：坐标格式转换
  - 单元测试：版本查询与 fallback
  - 单元测试：去重逻辑
- **提交信息**：`feat: add coordinate conversion and transitive dependency resolution`

### 3 冲突处理与 jex.toml 合并

- **功能目标**：将导入的依赖与现有 jex.toml 合并，处理冲突
- **文件结构**
  - 修改 `crates/jex-core/src/import.rs`：添加合并逻辑
- **接口设计**
  - 函数：`pub fn merge_with_existing(imported: &[String], existing: &HashMap<String, String>) -> HashMap<String, String>`
- **后端流程**
  1. 读取现有 jex.toml 的 `[dependencies]` 部分
  2. 对比导入的依赖与已有依赖
  3. 合并策略：
     - 新依赖：直接追加
     - 已有依赖（同坐标）：保留现有版本，不覆盖
     - 版本冲突（同 artifact 不同版本）：保留现有版本，打印警告
  4. 写回 jex.toml（仅修改 `[dependencies]` 部分，保留其他配置）
- **测试标准**
  - 单元测试：空 jex.toml 合并
  - 单元测试：无冲突合并
  - 单元测试：有冲突时保留现有版本
  - 单元测试：jex.toml 其他字段不被破坏
- **提交信息**：`feat: add dependency merge logic with conflict handling`

### 4 CLI `jex import maven` 集成

- **功能目标**：将导入逻辑接入 CLI，提供 `jex import maven <pom.xml>` 命令
- **文件结构**
  - 修改 `crates/jex-cli/src/main.rs`：将 `Commands::Import` 从 `planned()` 改为实际调用
- **接口设计**
  - 命令：`jex import maven [pom.xml 路径]`（默认当前目录 pom.xml）
  - 输出格式：
    ```
    📦 从 pom.xml 导入依赖

    解析到 5 个依赖：
      ✅ com.google.code.gson:gson:2.11.0
      ✅ org.slf4j:slf4j-api:2.0.9
      ⚠ junit-junit:4.13.2（scope=test，已跳过）

    导入完成！已添加 3 个依赖到 jex.toml
    ```
- **后端流程**
  1. 确定 pom.xml 路径（参数或当前目录）
  2. 调用 `parse_pom()` 解析
  3. 调用 `pom_to_jex_coords()` 转换坐标
  4. 调用 `resolve_transitive()` 解析传递依赖（可选，取决于 scope）
  5. 调用 `merge_with_existing()` 合并到现有依赖
  6. 写入 jex.toml
  7. 调用 `deps::update()` 生成/更新 jex.lock.toml
- **测试标准**
  - 集成测试：从 pom.xml 导入到空项目
  - 集成测试：从 pom.xml 导入到有依赖的项目（合并）
  - 集成测试：pom.xml 不存在时的错误提示
- **提交信息**：`feat: add jex import maven command`

## 设计核对点

- 使用已有的 `quick-xml` 依赖解析 pom.xml，不引入新 XML 库
- import 模块复用已有的 `resolver` 模块解析传递依赖
- merge 逻辑保留现有 jex.toml 配置不被覆盖
- scope=provided/test/runtime 的依赖默认跳过（可选包含）
- CLI 风格与现有命令一致（clap + anyhow 错误处理）
